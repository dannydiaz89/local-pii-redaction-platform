# `@local-pii/adapter-docx`

Bounded native DOCX inspection, extraction, and scan support for the rules-only local CLI profile.

This qualification slice accepts only strict, non-encrypted OOXML `.docx` ZIP packages whose visible text is contained in `w:t` nodes under paragraphs in `word/document.xml` and explicitly related headers, footers, footnotes, and endnotes. That includes ordinary body paragraphs and table-cell paragraphs. Supported parts are validated against both `[Content_Types].xml` and the main-document relationship graph, and are extracted in a deterministic order: document, numerically ordered headers, numerically ordered footers, footnotes, then endnotes. Header/footer relationship references and ordinary note IDs must resolve exactly; orphan text parts and orphan ordinary notes fail closed.

Text fragmented across formatting runs remains one native segment. A canonical `w:tab`, `w:footnoteReference`, or `w:endnoteReference` is a structural boundary: it contributes no visible value, splits adjacent text into distinct nonoverlapping source regions, and cannot be crossed by a detection or internal writer action. Standard reserved nonpositive-ID separator and continuation-separator notes are accepted only as zero-text structural notes with their matching self-closing marker. Non-whitespace character data outside `w:t` is rejected. Native DOCX locations remain the stable part name plus one-based paragraph ordinal; multiple tab-separated regions may share that native paragraph identity and are disambiguated by their canonical start/end coordinates. Unicode code-point actions are mapped back across the original run text nodes. Changed nodes are XML-escaped while untouched package-part bytes remain unchanged after decompression.

Two passive, non-content package profiles are also qualified without adding text to the canonical scan stream: one exact standard Office theme skeleton and a truly empty `webSettings.xml`. The theme profile requires exact namespace bindings, tag parents, multiplicities, top-level order, required attributes, numeric/color/enumeration grammars, standard theme names, and a closed common-typeface allowlist. Empty web settings require the exact bounded Microsoft namespace inventory and a closed `mc:Ignorable` prefix list. Unknown elements, reordered or missing required structure, prefix rebinding, arbitrary display names, character data, planted attribute canaries, orphan relationships, and wrong content types fail closed. Settings, font tables, custom XML, styles, numbering, and document properties remain blocked rather than being treated as passive.

At the ZIP boundary, stored entries and DEFLATE entries may use the standard compression-option bits and optional UTF-8-name flag. Names without the UTF-8 flag must be ASCII. Local extra fields remain blocked except for one bounded Microsoft OPC growth-hint field (`0xA220`) with its required signature, an exact initial-padding length, and zero-filled padding. Central-directory extras, arbitrary local extras, encrypted/data-descriptor entries, and covert nonzero growth padding remain blocked.

The adapter fails closed for macros, encryption, external relationships, metadata property parts, comments, images/drawings, `AlternateContent`, text boxes, fields, hyperlinks, revisions, hidden text, embedded objects, custom XML, structured document tags, styles, settings, font tables, numbering, non-qualified themes/web settings, unknown package parts, unsafe archive paths, duplicate entries, ZIP64, encrypted ZIP entries, and archive/resource-limit violations. XML input and internal writer replacements must satisfy the XML 1.0 character repertoire, including numeric entities. These features are not silently skipped. `FORMAT_UNSUPPORTED` exposes only a closed, value-free reason category; it never includes package part names, relationship targets, paths, or document values. The accepted surface remains intentionally narrower than ordinary Word-authored packages; blocked parts require their own canary inventory and sanitization rules before broader support is advertised.

The package includes an experimental native writer boundary that writes a normalized ZIP package to a private `0600` stage, validates its exact bytes, reopens it through this adapter, and publishes with the shared no-clobber hard-link boundary. It never modifies the input. The capability descriptor advertises only probe, inspect, extract, and scan with `EXTRACT_ONLY` assurance. Its `docx-extract-v1` profile attests only ZIP structure, the feature allowlist, and native source mapping; it is not redaction verification and cannot authorize publication. Redaction and verification must not be exposed by a composition root until a DOCX-native leakage verifier and fidelity evidence exist. Independent Office-renderer fidelity, sandboxed worker isolation, metadata sanitization policies, and broader DOCX parts remain Milestone 4 qualification work.

Hard limits currently include 25 MiB compressed input, 256 ZIP entries, 50 MiB total expanded content, 10 MiB per entry, 100× maximum compression ratio, 100,000 text nodes, 50,000 paragraphs, 10 million canonical code points, and 100,000 plan actions. Parsing is bounded but whole-document.

The implementation uses only Node built-ins for ZIP/DEFLATE handling; it introduces no parser or network dependency.
