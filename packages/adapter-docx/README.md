# `@local-pii/adapter-docx`

Bounded native DOCX inspection, extraction, and scan support for the rules-only local CLI profile.

This qualification slice accepts only strict, non-encrypted OOXML `.docx` ZIP packages whose visible text is contained in `w:t` nodes under paragraphs in `word/document.xml` and explicitly related headers, footers, footnotes, and endnotes. That includes ordinary body paragraphs and table-cell paragraphs. Supported parts are validated against both `[Content_Types].xml` and the main-document relationship graph, and are extracted in a deterministic order: document, numerically ordered headers, numerically ordered footers, footnotes, then endnotes. Header/footer relationship references and ordinary note IDs must resolve exactly; orphan text parts and orphan ordinary notes fail closed.

Text fragmented across formatting runs remains one native segment. A canonical `w:tab`, `w:footnoteReference`, or `w:endnoteReference` is a structural boundary: it contributes no visible value, splits adjacent text into distinct nonoverlapping source regions, and cannot be crossed by a detection or internal writer action. Standard reserved nonpositive-ID separator and continuation-separator notes are accepted only as zero-text structural notes with their matching self-closing marker. Non-whitespace character data outside `w:t` is rejected. Native DOCX locations remain the stable part name plus one-based paragraph ordinal; multiple tab-separated regions may share that native paragraph identity and are disambiguated by their canonical start/end coordinates. Unicode code-point actions are mapped back across the original run text nodes. Changed nodes are XML-escaped while untouched package-part bytes remain unchanged after decompression.

The expanded inspect/scan surface also validates bounded Word-generated settings, numbering, styles, font tables, core/extended document properties, and one exact zero-text bibliography `customXml` graph. These are not treated as opaque passive bytes. Free-form retained attributes and property text become isolated `DOCX_XML_VALUE` regions; generated `w:lvlText` templates are scanned even when they look numeric or hexadecimal. The auxiliary profiles enforce exact namespaces, closed element sets, parent graphs, deterministic child ordering, required identity attributes, per-part element ceilings, and hidden-style rejection. One exact standard Office theme skeleton and a truly empty `webSettings.xml` remain passive because every retained value is closed by grammar or allowlist.

External relationships remain blocked except for bounded `https:` and `mailto:` hyperlink targets owned by the main document or a supported header/footer/note part. The adapter never dereferences them. Every accepted target is an isolated `DOCX_RELATIONSHIP` canonical region, and every `w:hyperlink` reference must resolve exactly with no orphan relationship. A closed decorative `AlternateContent`/drawing/VML shape vocabulary is accepted only when it contains no text box, field, revision, hidden run, embedded object, or other text-bearing subtree; retained shape properties are scanned as XML-value regions rather than ignored.

At the ZIP boundary, stored entries and DEFLATE entries may use the standard compression-option bits and optional UTF-8-name flag. Names without the UTF-8 flag must be ASCII. Local extra fields remain blocked except for one bounded Microsoft OPC growth-hint field (`0xA220`) with its required signature, an exact initial-padding length, and zero-filled padding. Central-directory extras, arbitrary local extras, encrypted/data-descriptor entries, and covert nonzero growth padding remain blocked.

The adapter still fails closed for macros, encryption, non-hyperlink external relationships, comments, images or embedded binary objects, text boxes, fields, revisions, hidden text, structured document tags, non-qualified custom XML/drawings/themes/settings/styles/numbering/property shapes, unknown package parts, unsafe archive paths, duplicate entries, ZIP64, encrypted ZIP entries, and archive/resource-limit violations. XML input and internal writer replacements must satisfy the XML 1.0 character repertoire, including numeric entities. These features are not silently skipped. `FORMAT_UNSUPPORTED` exposes only a closed, value-free reason category; it never includes package part names, relationship targets, paths, document values, or planted element/attribute canaries.

Version 0.5 extends the experimental native writer boundary across the complete typed carrier surface accepted for scan: paragraph/run text, `DOCX_RELATIONSHIP` targets, and `DOCX_XML_VALUE` attribute/text carriers. The XML scanner binds every carrier to an exact owning part and raw decoded-value range. Unicode code-point actions must remain inside one canonical region; transformed attribute/text values are XML-escaped for their original quote context, external targets are reparsed against the closed HTTPS/mailto grammar, and the complete rewritten package is reparsed before a private stage is created. The writer writes a normalized ZIP package to a private `0600` stage and uses the shared no-clobber hard-link boundary. It never modifies the input.

A bounded adapter-local reconciliation foundation binds the immutable plan and writer receipt, reproduces the expected native bytes, reopens and validates the ZIP/OOXML graph, reconciles exact canonical replacements and every retained carrier, proves untouched decompressed package-part contents remain byte-identical, and rejects uniquely planted planned-source canaries. Synthetic tests cover fragmented run actions, relationship targets, Word/drawing attributes, property text, multi-part/multi-carrier ordering, both XML quote styles, entity-special and astral replacements, invalid post-rewrite relationship grammar, forged receipts, mutation detection, and cleanup. This is complementary evidence only: the foundation deliberately reports `RECONCILED_NONINDEPENDENT`, reuses the extraction parser, and is not fidelity-qualified. ZIP flags, extras, timestamps, and compressed bytes are normalized by the experimental writer and are not claimed byte-identical.

The capability descriptor therefore continues to advertise only probe, inspect, extract, and scan with `EXTRACT_ONLY` assurance. Its `docx-extract-v1` profile attests only ZIP structure, the feature allowlist, and native source mapping; it is not redaction verification and cannot authorize publication. Redaction and verification must not be exposed by a composition root until a separate `docx-redact-v1` route independently enumerates and rescans all retained parts/carriers and fidelity evidence exists. Independent Office-renderer fidelity, sandboxed worker isolation, metadata sanitization policies, malicious-corpus qualification, and broader DOCX parts remain Milestone 4 work.

Hard limits currently include 25 MiB compressed input, 256 ZIP entries, 50 MiB total expanded content, 10 MiB per entry, 100× maximum compression ratio, 100,000 text nodes, 50,000 paragraphs, 10,000 XML/relationship carrier regions, 2,048 code points per carrier, 10 million canonical code points, and 100,000 plan actions. Parsing is bounded but whole-document.

The implementation uses only Node built-ins for ZIP/DEFLATE handling; it introduces no parser or network dependency.
